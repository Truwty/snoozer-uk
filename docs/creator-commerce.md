# Creator commerce — foundation work in progress

Current implementation: private profile-scoped product drafts, plain-text title/description, integer GBP prices, optimistic revisions and reversible archive/restore. Five active and twenty total drafts per account, including all profiles and archived entries. Available on all plans during foundation development. These are metadata quotas, not an entitlement to sell. No files, public products, checkout, buyer access or connected accounts have been implemented. No Buy button, paid product advertisement or payout is enabled. Migration67 is not hosted yet.

Boundaries: verified authenticated owners only; private table with no direct role access, including service_role. Owner RPCs validate ownership, input and account-wide quotas in PostgreSQL. The account lock serializes catalogue changes and profile deletion. Drafts do not affect profile publication/revisions, aliases, schedules or public payloads. Plain text is React-escaped. Archiving retains content and frees an active slot; archived products still consume the total cap. Profile/account deletion currently cascades only unsold private metadata. That must change before orders or buyer entitlements exist. No storage, provider keys, dependency or paid resource is added by this slice.

## Proposed Connect model — sandbox implementation decision, live release unapproved

Accounts API: Accounts v2, explicit `dashboard: full`, `defaults.responsibilities.fees_collector: stripe`, `losses_collector: stripe`, merchant configuration and requested card_payments. No legacy account type, platform transfers, recipient-only accounts or public-preview Express configuration. Independent creators sell their own digital products and own the customer relationship; direct charges keep the payment in the creator's connected account. This is a software-platform model, separate from existing Snoozer premium subscriptions and Ko-fi support links.

Creator onboarding: authenticated verified owner explicitly starts onboarding; the server creates exactly one sandbox account per owner with an idempotent operation binding. Stripe-hosted onboarding collects sensitive identity and business details directly. Return navigation is not proof of completion. Retrieve current capability status (`configuration.merchant.capabilities.card_payments.status`) and permitted responsibilities before every new Checkout, and recheck ongoing requirements. Full Dashboard access uses Stripe's normal account login. No identity data, country eligibility or agreement acceptance is fabricated by Snoozer or the agent.

Hosted onboarding avoids a new embedded dependency. Embedded account_onboarding, notification_banner, account_management, payments and payouts components remain an optional future in-app enhancement; the notification banner is required if that embedded route is introduced. Current full Dashboard/hosted requirement-remediation links must serve that operational need before release. The planner's embedded/custom-only tree omitted the officially supported hosted option; it has not been accepted with a false embedded selection.

Negative balance liability: the proposed full/stripe/stripe direct-charge combination assigns connected-account negative balances to Stripe. This does not remove Snoozer's platform policy duties or guarantee legal eligibility.

Risk management: creators handle refunds/disputes in their full Dashboard; Snoozer must verify connected-account events and suspend digital delivery on refunds, disputes or fraud signals. Seller/content moderation, safe file handling, support, restricted-product enforcement and abuse controls remain release requirements. Radar for Platforms is a possible additional control, not provisioned or promised free.

Funds: buyer → creator connected-account charge → Stripe processing fees → creator balance. No platform transfer, held customer balance or payout scheduling. Sandbox platform transaction fee is zero (`application_fee_amount` omitted), pending an explicit commercial pricing decision. No estimated Stripe fee gross-up. Existing SaaS subscription fees continue through the existing platform billing implementation; do not migrate those customers or invent customer_account mappings. Actual costs depend on region/method: [Stripe pricing](https://stripe.com/pricing).

Webhook integration: verify the signature of the dedicated sandbox connected-account event destination, reject livemode/mismatched account data, and persist idempotent receipts before reconciliation of current provider state.

## Required remaining implementation and verification

1. Private bounded product file upload/storage with actual byte/type verification, shared account media quota, permissioned attachment download, retry/discard/cleanup and deletion protection. No public bucket or user-supplied fetch URL.
2. Sandbox-only Connect configuration, owner-bound onboarding and capability refresh. Exact account-country/merchant model and live fee/legal/tax decisions remain gates. No connected-account creation or agreement has been submitted yet.
3. Public storefront only behind an explicit sandbox flag and seller-ready/product-ready checks. Immutable purchased price/file version, one creator/order, verified buyer identity and durable pending Checkout binding before creating a session. Server selects price, product, account and return URLs. No client payment-status grants.
4. Signed connected-account events plus current provider retrieval for payment status, amount/currency/product/order/owner scope. Idempotent receipt processing, missed-event recovery and out-of-order protection. Partial/full refunds and dispute/fraud holds must revoke delivery; a late success cannot erase a hold.
5. Buyer-scoped receipts and short-lived permissioned attachment delivery with no shared email-only secret, public object URL or cross-owner access. Archive/unpublish stops new purchases while preserving previously purchased access. Refund/support workflows and bounded retention must be explicit.
6. SQL/unit/disposable browser tests, actual sandbox onboarding/Checkout/refund/provider delivery, accessibility and phone checks. Live commerce remains off until all required capability, legal/tax, operational and security gates are approved.

The Stripe connector exposes only the live Lingua account. Used for advisory planning/documentation only; no live mutation. Existing staging test-mode credentials remain provider-side and have not been copied locally. Do not infer that existing billing-key permissions include Connect or use the live connector as a sandbox substitute.
